## Иерархия исключений

Корень — класс `Throwable`; под ним два семейства: `Error` и `Exception`.

```mermaid
classDiagram
    Throwable <|-- Error
    Throwable <|-- Exception
    Exception <|-- RuntimeException
    Exception <|-- IOException
    RuntimeException <|-- NullPointerException
    RuntimeException <|-- IllegalArgumentException
    RuntimeException <|-- ArithmeticException
    RuntimeException <|-- IndexOutOfBoundsException
    RuntimeException <|-- ClassCastException
    RuntimeException <|-- IllegalStateException
    Error <|-- OutOfMemoryError
    Error <|-- StackOverflowError
```

### `Throwable`

Базовый класс всех объектов, которые можно бросить (`throw`) и поймать (`catch`).

### `Error`

Серьёзные проблемы JVM, обрабатывать не следует: `OutOfMemoryError`, `StackOverflowError` (см. [[04. Методы и параметры#StackOverflowError|StackOverflowError]]).

### `Exception`

Ошибки программы, которые стоит обрабатывать. Делится на checked и unchecked.

### `RuntimeException`

Неконтролируемые исключения — ошибки логики программы (см. [[#Unchecked exceptions|unchecked]]).

### Частые исключения и их причины

| Исключение | Тип | Типичная причина |
| --- | --- | --- |
| `NullPointerException` | unchecked | обращение по `null`-ссылке |
| `ArithmeticException` | unchecked | деление целых на ноль |
| `IndexOutOfBoundsException` | unchecked | выход за границы массива/списка |
| `ClassCastException` | unchecked | некорректное приведение типов (см. [[01. Основы языка Java#Приведение ссылочных типов|приведение]]) |
| `IllegalArgumentException` | unchecked | некорректный аргумент |
| `IllegalStateException` | unchecked | объект в недопустимом состоянии для операции |
| `NumberFormatException` | unchecked | парсинг нечисловой строки (см. [[13. Дата, время, числа и полезные API#Парсинг чисел|парсинг]]) |
| `UnsupportedOperationException` | unchecked | операция не поддерживается (см. [[10. Коллекции и структуры данных#Неизменяемые коллекции|неизменяемые коллекции]]) |
| `ConcurrentModificationException` | unchecked | модификация коллекции при итерации (см. [[10. Коллекции и структуры данных#Итераторы|итераторы]]) |
| `IOException` | checked | ошибка ввода-вывода |
| `FileNotFoundException` | checked | файл не найден |

## Checked exceptions

Компилятор **требует** их обработать (`try/catch`) или объявить (`throws`). Типичны для ввода-вывода: `IOException`, `FileNotFoundException` (см. [[12. Ввод-вывод, файлы и сериализация|ввод-вывод]]).

```java
void readFile(String path) throws IOException {   // объявлено
    Files.readString(Path.of(path));
}
```

## Unchecked exceptions

Наследники `RuntimeException`. Обрабатывать не обязательно. Возникают при ошибках логики: `NullPointerException`, `IllegalArgumentException`, `ArithmeticException`, `IndexOutOfBoundsException`.

```java
int[] a = new int[3];
int x = a[10];   // ArrayIndexOutOfBoundsException — не требует обработки
```

## `try` и `catch`

```java
try {
    int r = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println("Деление на ноль: " + e.getMessage());
}
```

Если исключение не поймано ни одним `catch` — распространяется вверх по стеку вызовов.

### Методы `Throwable`

```java
e.getMessage()      // текстовое сообщение
e.getLocalizedMessage()  // локализованное сообщение
e.printStackTrace() // трасса стека в stderr (см. [[15. JVM, память и профессиональная разработка#Отладка|отладку]])
e.getStackTrace()   // StackTraceElement[] — кадры стека
e.getCause()        // причина (см. [[#Цепочки исключений|цепочки]])
e.addSuppressed(t)  // добавить suppressed-исключение
e.getSuppressed()   // suppressed-исключения (см. [[#Suppressed exceptions|suppressed]])
```

### Полная форма `try-catch-finally`

```java
try {
    risky();
} catch (IOException e) {
    // обработка
} finally {
    // всегда выполнится
}
```

Ветки `catch` и `finally` могут сочетаться, а `try` обязан иметь хотя бы одну из них.

## Несколько `catch`

Порядок важен: более специфичное исключение должно идти раньше общего.

```java
try {
    readFile(path);
} catch (FileNotFoundException e) {
    System.out.println("Файл не найден");
} catch (IOException e) {
    System.out.println("Ошибка ввода-вывода");
}
```

Если `catch (IOException)` поставить первым — `FileNotFoundException` никогда не обработается отдельно.

## Multi-catch

С Java 7 один блок ловит несколько несвязанных типов (через `|`):

```java
try {
    // операции
} catch (IOException | SQLException e) {
    e.printStackTrace();
}
```

Типы в multi-catch не могут быть в отношении наследования (тогда нужен общий предок).

## `finally`

Выполняется **всегда** — и при нормальном завершении, и при исключении, и при `return`. Для освобождения ресурсов.

```java
try {
    risky();
} finally {
    System.out.println("Всегда выполнится");
}
```

Современная альтернатива для ресурсов — try-with-resources (см. [[#Try-with-resources|try-with-resources]]).

### Подводный камень: `return` в `finally`

`return`/`throw` в `finally` **перекрывает** результат и исключение из `try` — результат теряется, исключение «съедается»:

```java
int f() {
    try {
        return 1;
    } finally {
        return 2;   // итог: 2, значение 1 потеряно
    }
}
```

Исключение из `try` тоже будет подавлено. Поэтому `return`/`throw` в `finally` — антипаттерн.

## `throw`

Явное выбрасывание исключения:

```java
void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException("Возраст не может быть отрицательным");
    }
}
```

`throw` прерывает выполнение метода — код после `throw` недостижим.

## `throws`

Объявление в сигнатуре: метод может бросить проверяемое исключение.

```java
void connect() throws IOException { ... }
```

Если метод бросает несколько checked исключений — перечисляются через запятую. Перечислять unchecked не требуется.

`throws` не обрабатывает исключение — только предупреждает вызывающего. Объявление checked исключения без выбрасывания — допустимо, но бессмысленно.

## Создание собственных исключений

Наследуют `Exception` (checked) или `RuntimeException` (unchecked):

```java
class InsufficientFundsException extends RuntimeException {
    public InsufficientFundsException(String message) {
        super(message);
    }
    public InsufficientFundsException(String message, Throwable cause) {
        super(message, cause);   // с причиной (см. [[#Цепочки исключений|цепочки]])
    }
}
```

### Checked или unchecked?

| | Checked (`Exception`) | Unchecked (`RuntimeException`) |
| --- | --- | --- |
| Обязателен ли `throws`/`catch` | да | нет |
| Когда | ошибки, которые вызывающий **должен** учесть | ошибки программиста, которые **не ожидаются** в норме |
| Примеры в JDK | `IOException`, `SQLException` | `IllegalArgumentException`, `NPE` |

Общее правило: для ошибок, которые вызывающий обязан обработать (нет сети, нет файла), — checked; для багов логики и нарушения предусловий — unchecked.

Практика: доменные исключения с говорящими именами и удобными конструкторами.

## Повторное выбрасывание исключений

Поймав, можно перебросить то же или обёрнутое исключение:

```java
try {
    risky();
} catch (IOException e) {
    System.out.println("Логируем");
    throw e;   // переброс
}
```

С Java 7 точный повторный проброс (precise rethrow) сохраняет конкретный тип для `throws`.

## Цепочки исключений

Сохранение причины исходной ошибки.

### `getCause`

```java
try {
    doWork();
} catch (SQLException e) {
    throw new ServiceException("Не удалось сохранить", e);   // причина
}
```

Чтение причины при отладке:

```java
Throwable root = e.getCause() != null ? e.getCause() : e;
root.printStackTrace();
```

Причина — исходное исключение; вложенные обёртки дают цепочку причин (обход до корня через цикл по `getCause()`).

### Конструкторы с причиной

У большинства исключений есть конструктор `(String message, Throwable cause)`. Причина доступна через `e.getCause()` — полезна при отладке.

Рекомендуется всегда передавать причину при оборачивании, иначе корень проблемы теряется.

## Try-with-resources

С Java 7 — автоматическое закрытие ресурсов, реализующих `AutoCloseable`.

### `AutoCloseable`

Интерфейс с единственным методом `close()`. Реализуют потоки, файлы, соединения (см. [[12. Ввод-вывод, файлы и сериализация|ввод-вывод]]).

### Автоматическое закрытие ресурсов

```java
try (var br = new BufferedReader(new FileReader("data.txt"))) {
    String line = br.readLine();
    System.out.println(line);
}
// br.close() вызывается автоматически, даже при исключении
```

Несколько ресурсов:

```java
try (var in = new FileInputStream("a.bin");
     var out = new FileOutputStream("b.bin")) {
    in.transferTo(out);
}
```

### Suppressed exceptions

Если при закрытии ресурса бросается исключение, оно добавляется как suppressed к основному. Доступны через `e.getSuppressed()`. Это важно: исключение из `close()` не должно «съедать» исключение из тела.

## Исключения и переопределение методов

Переопределяющий метод не может бросать **более широкие** checked исключения, чем метод суперкласса (см. [[06. Наследование и полиморфизм#Переопределение методов|переопределение]]).

```java
class Base {
    void work() throws IOException { }
}
class Sub extends Base {
    @Override
    void work() throws IOException { }   // ок
    // void work() throws Exception { }  // ошибка: шире IOException
}
```

Unchecked исключения этим правилом не ограничены.

## Практика проектирования исключений

- Использовать исключения для **исключительных** ситуаций, не для обычного потока управления.
- Проверять входные данные заранее (`if (x < 0) throw ...`) вместо глубоких каскадов исключений.
- Ловить как можно уже; не глотать исключения пустым `catch`.
- Обёртывать низкоуровневые исключения в доменные (см. [[#Цепочки исключений|цепочки]]), сохраняя причину.
- Не использовать исключения для завершения циклов и не обрабатывать `Error`.
- Документировать броски в Javadoc через `@throws` (см. [[15. JVM, память и профессиональная разработка#Документирование Javadoc|Javadoc]]).
- Исключения — не замена результату: «нет значения» лучше выражать через `Optional`/`null`, а не исключением (см. [[13. Дата, время, числа и полезные API#Optional|Optional]]).
- **Логировать на границе**: не логировать и не перебрасывать в каждом слое — логировать один раз, где исключение обрабатывается окончательно.
- **`fail-fast`**: проверять предусловия в начале метода (`requireNonNull`), а не ловить `NPE` позже.

## Распространённые антипаттерны

```java
// плохо: пустой catch — глотает ошибку
try { risky(); } catch (IOException e) { }

// плохо: catch Throwable — ловит и Error, маскирует серьёзные проблемы
try { risky(); } catch (Throwable t) { log(t); }

// плохо: исключение как поток управления
try {
    int v = Integer.parseInt(s);
} catch (NumberFormatException e) {
    // парсинг «не удался» — но это ожидаемое условие, а не исключительное
}
```

Вместо последнего — проверка заранее или `OptionalInt` через `parseInt`-обёртку.
